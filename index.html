Campus Guide

A web app that guides first-year students from the entrance to their lecture room, tested with students on campus.

Context
Elective module User Experience Engineering, HTW Saar. L2, semester 4
Type
Academic team project, four students
My part
User research, persona, Lean UX Canvas, MVP analysis, test preparation
Tools
Paper prototype, HTML/CSS/JavaScript prototype (by a teammate), GitHub Pages
User Research Persona Ideation Wireframes Prototype Usability Test Reflection

Overview

In the elective module User Experience Engineering, our team of four picked a problem we knew from experience: finding rooms on the Alt-Saarbrücken campus of HTW Saar. Some of us had been late to class because of it.

The report and the prototype are in German.

Problem

Students, mostly first-years, lose time and arrive late because the campus is hard to read: confusing building numbers, an unclear structure and little signage. The first weeks are the hardest, and breaks of 15 minutes leave no time for detours.

Goals

  • Business goal in our Lean UX Canvas: raise punctuality by 5% by the next semester start. It is a target we set, not a measured result.
  • MVP limited to Building 8 so that floor plans stay readable on a phone.
  • Core features: room search, building display, route from the main entrance to the room.

My role and the team

We were four students and shared the work. The table separates what I did from what the team did.

User research

We observed and interviewed 15 students on campus, mostly first-years, who have the most trouble with first orientation. We interviewed without a fixed script so we could adapt questions to the place, then sorted and counted the answers.

We focused on the orientation problems (numbering, building structure and signage) and set aside ramps, parking and break length for a later round.

Persona

Our key persona, Emma, is a first-semester student who wants to arrive on time because some lecturers do not admit latecomers. She drives, parks, and finds her way with her phone. Her key need: know quickly which building her next room is in and how to get there, because breaks of 15 minutes leave no time for detours.

Ideation

We brainstormed in a group chat so that team members who were ill could take part. We allowed deliberately absurd ideas, such as a robot dog that walks ahead, smart glasses and drones. They raised the number of ideas and lowered inhibitions. The text chat made clustering hard, so a shared visual board would have worked better.

We combined a room finder with route search and QR codes, because it works on the phone students already have.

Wireframes

The team sketched wireframes and a paper prototype with the QR code as the starting point.

Prototype

The high-fidelity MVP: search, route with an arrow, step-by-step text. The interface is in German.

  1. Scan a QR code at the entrance of Building 8. The main entrance becomes the fixed starting point, with no install and no sign-up.
  2. Type a room number. Suggestions appear while typing and the right floor plan opens.
  3. Follow a bright line with an arrowhead, with text steps such as "Take the stairs up two floors".
  4. Switch on the accessible mode to route through the elevator instead of the stairs.
  5. See a success screen at the door.

The prototype is plain HTML, CSS and JavaScript with the route drawn on a canvas. There is no backend, so it loads fast on campus Wi-Fi.

We tested the prototype with four students at the entrance of Building 8, using think-aloud and a SUS questionnaire. They started from the QR code, found a room, followed the route to another floor, and tried the accessible mode.

Limiting the scope to one building let us finish a tested product. Extending it to the rest of the campus and adding indoor positioning are the next steps.

Four testers are enough to find the big problems, not enough to claim a general score. And next time I would run the brainstorm on a shared board, as we noted in the report.

Learning a Language with Netflix

A UX study of Netflix: a survey, a persona, tests of the current app, and a concept for a language-learning mode.

Context
Human-computer interaction course, ISFATES. L2, semester 3
Type
Academic project, individual
My part
Everything: research, synthesis, ideation, concept and tests
Tools
Miro, Google Forms, Figma
User Research Persona Ideation Concept Design Usability Test Reflection

Overview

Netflix is one of the most used interfaces in the world, and I use it every week. For my HCI course I treated it as a case: where does a leading product still make people work harder than they should?

The report follows four phases: explore, ideate, generate and evaluate.

Problem

Two themes came back in every step. Choosing takes too long in a very large catalogue, which causes decision fatigue. And some viewers already use Netflix to practise languages, but the interface gives them little support for it.

Goals

  • Understand how people choose what to watch and what frustrates them.
  • Explore ideas in a structured way, not only the first one that comes to mind.
  • Check the current app with real users, and turn the findings into one concept.

My role

This was an individual project. I ran the survey, synthesised the answers, led the ideation, designed the concept and ran the tests of the current app.

User research

I wrote a short survey of 8 questions and shared it through WhatsApp and with people around me. It collected 13 answers.

10 / 13of 13 chose an improved offline mode as the feature to add (several choices allowed)
4 / 13chose better search filters

Thirteen answers from my own circle are a small, informal sample. They guided my thinking but prove nothing general.

Persona and synthesis

I turned the answers into a persona, an empathy map and an experience map that follows a viewer's path to find pain points. The persona is a 26-year-old polyglot who watches daily on tablet and TV, practises languages with series, and is frustrated by slow choosing and imprecise subtitles.

From observations to the concept

ObservationNeedIn the concept
Choosing takes too long in a very large catalogue (decision fatigue)A shorter way to a good pickTitles already matched to the chosen language and level

Offline mode was the most chosen feature in the survey (10 of 13). The language-learning concept builds on the persona and the ideation rather than on that top answer. The links in this table are my reasoning, not tested results.

Ideation

  • UX Devil. Describe the worst possible experience, then turn each point into a fix.
  • Lotus Blossom. Grow one theme into eight, then each of those into eight more.
  • Storyboard. Three frames showing a learner who moves from a rigid course to learning through series.

Concept design

A new Learn a language tab. The viewer picks a language and a level, from beginner to advanced, and gets titles matched to that level. Extra panels cover vocabulary and pronunciation, and a progress view shows the level reached.

The visual at the top of this page is the redrawn concept: one clear path from language, to level, to titles, with progress kept on the side.

Usability test

Tested: the existing Netflix app (expert review, user test, SUS). Not tested yet: my language-learning concept.

An expert review of the existing app against six groups of criteria found strong guidance and error handling, and weaker results on cognitive load and user control, mostly because of intrusive automatic playback.

Five users then completed four scenarios on mobile and TV: change the download language, find My List, set parental control, and remove a finished series from Continue Watching. They liked autoplayed trailers and the easy offline mode. They struggled with three things:

  • A busy TV home screen. Users asked for a calm mode without autoplaying video.
  • Having to start playback before they can change the language of a download.
  • A thumbs up and down that feels too coarse to tell the algorithm what they dislike.
94SUS score out of 100 for the current app, from a small sample

Reflection and next steps

I designed the concept from the survey and the persona, but I tested only the current interface. Next time I would put the new tab in front of users too, to check whether it meets the needs I identified.

A SUS of 94 says the product is easy to use. It does not say what to improve. The observed test sessions gave me the useful findings.

This is an academic study of a third-party product. It is not affiliated with Netflix, and all Netflix names belong to their owner.

International Student Guide

A practical guide that turns scattered administrative rules into a clear timeline for students joining the Franco-German programme from outside the EU.

Context
DFHI-ISFATES, in collaboration with M. Hoffmann
Status
In finalisation
My part
Research, writing, information structure and layout
Format
Canva, A5, 64 pages
Structure Design Choices Accuracy Reflection

Some original project visuals cannot be displayed publicly due to publication rights restrictions.

Overview

Students from outside the EU who start the ISFATES programme have to handle many administrative steps before and during their studies: application, enrolment, visa, health insurance, housing and the move between France and Germany. Students from Cameroon, for example, join through a partnership with HITAS Douala. They start in Metz at the Université de Lorraine, then continue in Saarbrücken at HTW Saar. L2 students of the GCME specialisation also have a site in Luxembourg.

The information sits on different university websites, official portals and internal documents. Procedures, offices and deadlines change from one country and one situation to the next.

Problem

How can scattered, sometimes complex administrative information be structured so that a new international student sees what applies to them, when to act and what comes next?

I designed for five situations: first orientation, concrete preparation (documents, deadlines, fees, offices), ongoing studies, the move between countries, and reading in more than one language. These profiles come from the project context. They are not personas validated by interviews.

Information structure

Instead of grouping content by institution or by administrative topic, I organised it along a student's path in three phases:

  • Before the programme: application, admission, enrolment, insurance, visa, funding and housing.
  • During the programme: the academic year, re-registration, life at each site, and the specifics of the Luxembourg route.
  • After the programme: further study and, where the conditions are met, the first steps toward working.

Every procedure answers the same questions: what is it, who is it for, when must I act, where is the office, which documents, what costs and deadlines, and who can I ask.

Design choices

  • Hierarchy. Navy blue bands (#1B2A4A) are the recurring anchor for headings, cards and frames, to help readers move between topics.
  • Content categories and callouts. À retenir, Attention and Bon à savoir separate the essentials from the warnings and the extras.
  • Visible consequences. Rules with serious effects, such as the limit of three exam attempts, must be easy to find.
  • Languages. The guide is mostly in French. German administrative terms such as Rückmeldung stay where students will meet them, and the Saarbrücken section is in German.

Accuracy

With administrative content, a wrong detail can cost a student a deadline or a visa. So checking the facts was part of the design work:

  • Rules are checked against official sources. The exam-attempt rule is verified against the current regulations before any emphasis is final.
  • Details that change, such as fees, deadlines and grant amounts, are rechecked before publication. Where a fee could not be confirmed, the guide points to the official page instead of printing a number.
  • The French or German quota status is kept apart from the study location, because every student starts in Metz. The quota status affects the administrative assignment and when the DFH grant is paid.
  • Residence rights after studying distinguish a Bachelor from a Master. The APS is covered only for a Master's degree.

Reflection and next steps

Designing an information document is more than layout and type. Choosing, ordering and verifying the content matters as much. A timeline helps match rules to real moments, but it forces care with special cases, country-specific procedures and facts that change.

The guide is still being finalised and has not been tested with students, so I make no claim about results. Next steps: the final content check, updating the details that change, and a test with students from the target group. Can they find what they need quickly, follow the order of the steps, and understand the critical warnings?

AufgabenManagement

A Java console app that speaks German, French or English and shows dates, numbers and currency the way each country expects.

Context
Java course at DFHI, November 2026
Type
Individual course project
My part
Requirements, decisions, final version. Code written with substantial AI support
Tools
Java 17, ResourceBundle, MessageFormat, Properties, Maven
Assignment My role ResourceBundle MessageFormat Locale Maven Why it matters for UX Learnings and limits

Overview

The starting point was an existing console program whose texts were all written in German directly in the code. It asks for a consultant's details and prints a task overview with dates and amounts. The task was to make it multilingual.

The assignment

  • Switch between German, French and English while the program is running.
  • Choose the start language from the command line, from the last language saved in a config file, or from the language of the Java runtime, in that order.
  • Pay attention to software architecture and quality, and build a runnable JAR file with Maven.

My role

Individual course project. I set the requirements: keep the original program as the base, keep the solution simple enough to explain, German as the default language. I rejected a first draft that was too complex, turned the professor's feedback into concrete changes and chose which variant went into the final version.

The code was written with substantial help from an AI assistant (Claude Code). My project report documents which steps were mine and which came from the AI.

ResourceBundle

What it is

A Java mechanism that loads the texts of an app from one file per language. The code only asks for a key, such as overview.header, and gets the text in the current language.

In this project

All visible texts, from prompts to error messages, are in three files, messages_de, _fr and _en.properties, with the same keys. The bundle is loaded without a fallback, so Java never silently switches to the system language.

private static void loadBundle(String languageCode) {
    currentLocale = toLocale(languageCode);
    bundle = ResourceBundle.getBundle(BUNDLE_NAME, currentLocale, NO_FALLBACK);
}

Why it matters

The interface can be translated without being reprogrammed. For design, this means texts are content, not part of the layout: a mockup should not depend on one fixed wording, and every label needs a clear name the team can refer to.

MessageFormat

What it is

A Java class that fills the placeholders in a text and formats them for the current language. The same date reads “11 Nov 2026” in British English and “11.11.2026” in German.

In this project

Each text says how its values are shown, for example {0,number,currency} for an amount. Plurals use a choice pattern, so the app writes “one task” or “3 tasks”, never “1 tasks”. Forms of address (Mr/Ms, Herr/Frau, M./Mme) also come from the language files.

overview.tasks = {1,choice,0#{0} has not completed any tasks yet.|1#{0} has completed one task.|1<{0} has completed {1,number,integer} tasks. That is a lot.}

Why it matters

Plurals, word order and forms of address change from one language to the next. When UI copy is written as a pattern with placeholders rather than as finished sentences, it can be localised without rewriting the code.

Locale

What it is

A Java object that stands for a language and a country, such as de-DE or en-GB. It decides how dates, numbers and currency are formatted.

In this project

Each language is tied to a country, so the currency symbol follows it (€ or £). The amount itself is not converted. The chosen language is saved in config.properties and restored at the next start.

private static Locale toLocale(String languageCode) {
    return switch (languageCode) {
        case "fr" -> Locale.FRANCE; // fr-FR
        case "en" -> Locale.UK;     // en-GB
        default -> Locale.GERMANY;  // de-DE
    };
}

Why it matters

Language and country are not the same thing: English in the UK and in the US use different date formats and currencies. Remembering the user's choice spares them from setting it again at every start. Both are design decisions, not only code.

Maven

What it is

The tool that compiles a Java project and packages it, for example into a .jar file that can be started with one command.

In this project

mvn clean package builds aufgabenmanagement.jar, with the three language files inside.

Why it matters

Knowing how a project is built helps me understand what it takes to ship a change, and talk about it with developers in their terms.

Why this matters for a UX/UI internship

Designing for several languages starts before translation. German texts are often longer than English ones, so buttons and labels need room to grow, and dates, amounts and forms of address must fit each country. This project showed me how localisation works on the code side, so I can plan for it in mockups and discuss it with developers.

What I learned and limits

I learned to keep content apart from code and to treat a text as a pattern with placeholders. The first AI draft was too complex; a simple structure that I could explain worked better.

Limits: it is a console app without a graphical interface, and it was not tested with users.

Playwright Reservation Tests

Automated tests that check whether a two-step booking form behaves the way a user expects.

Context
Java course at DFHI, autumn 2026
Type
Individual course project
My part
Test setup, page objects, test scenarios, fixes to the form's JavaScript
Tools
Java, Playwright for Java, JUnit 5, Maven
Assignment My role Playwright JUnit 5 Page Object Model Maven Why it matters for UX Learnings and limits

Overview

The application has two pages. The first is a reservation form: a name, “with” or “without alcohol”, and at least one preference such as karaoke. The second is a confirmation page. The tests use both pages like a visitor would and check what appears on the screen.

The assignment

  • Test the functional requirements of the two-page application automatically with Playwright and JUnit 5.
  • Organise the tests with the Page Object Model, following a given UML class diagram.
  • Following the lecturer's feedback: test our own HTML/JavaScript logic, not Playwright itself, and describe each test as a Given/When/Then scenario.

My role

Individual course project. I set up the test environment, wrote the page objects and the test scenarios, and corrected the form's JavaScript so that a saved reservation is loaded back into the form and the validation runs again.

I used AI to structure the test ideas and to refactor the code into the Page Object Model, then checked and adapted the result myself.

Playwright

What it is

A tool that opens a real browser and uses a web page the way a person would: it types, clicks and reads what is on the screen.

In this project

The tests check that the “Reservieren” button stays disabled while a required field is empty, that the confirmation page shows the right name and choices, that a reservation can be changed, and that the confirmation page shows a notice when it is opened without data.

resPage.selectAlcohol(false);
resPage.selectPreference("tanzen");
resPage.tryClickReserveForced();

assertAll("Der Button muss deaktiviert bleiben, da kein Name eingegeben wurde",
        () -> assertEquals("", resPage.getNameInputValue()),
        () -> assertFalse(resPage.isReserveButtonEnabled()),
        () -> assertTrue(page.url().endsWith("Reservierung.html"))
);

Why it matters

These are behaviours a user notices straight away: a button that does nothing, a wrong summary, lost data. Automated tests catch them again after every change, without anyone clicking through the form by hand.

JUnit 5

What it is

The standard Java framework for writing and running tests. Each test has a name and checks, and a report shows which tests passed.

In this project

Each test starts with a Given/When/Then description and has a readable German name. Several checks are grouped with assertAll, so one failure does not hide the others.

/**
 * - GIVEN der Benutzer ist auf der "Reservierung"-Seite AND das Namensfeld ist leer
 * - AND er wählt "ohne Alkohol" und "Tanzen"
 * - WHEN er versucht, auf "Reservieren" zu klicken
 * - THEN ist der Button deaktiviert AND er bleibt auf der "Reservierung"-Seite.
 */
@Test
@DisplayName("Button deaktiviert, wenn der Name fehlt")

Why it matters

Readable test names form a list of expected behaviours that the whole team can read, not only developers.

Page Object Model

What it is

A way to organise tests: each page of the application gets its own class, which describes what a user can do on that page.

In this project

ReservierungPage offers actions such as entering a name or choosing a preference. BestaetigungPage reads the welcome message and the summary. The tests only talk to these page objects.

public void enterName(String name) {

Door State Machine

A Java class that simulates a door with a PIN code: it opens, closes, locks, unlocks and locks itself again after a while.

Context

Assignment My role State Machine UML TDD JUnit 5 Why it matters for UX Learnings and limits

Overview

The class has three states: open, closed and locked. It counts how often the door was opened, needs a four-digit PIN to unlock and locks itself when it stays closed. It shows nothing on screen: it is the logic an interface could be built on.

The assignment

  • Open, close, lock and unlock the door; unlock only with a four-digit PIN.
  • Lock automatically after 5 seconds in the closed state, and count how often the door was opened.
  • Handle every invalid operation, with no console output in the class.
  • Complete tests with JUnit 5, developed test-first.

My role

Individual course project. Before writing any code, I analysed the door as a state machine and drew the UML state diagram. Then I wrote the class and the tests. After the professor's feedback, I replaced text error messages with error codes and cleaned up the tests.

I used an AI assistant (Claude) to understand the assignment, explain Java concepts and review my code. The report lists my prompts; I decided what to keep.

State Machine

What it is

A model in which something is always in exactly one state, and only certain actions move it to another state.

In this project

The three states are OPENED, CLOSED and LOCKED. Each method first checks the current state: a valid action changes it, any other action raises an error with a precise code, such as IS_LOCKED or WRONG_PIN.

public void open() throws DoorException {
    switch (state) {
        case OPENED -> throw new DoorException(DoorException.ErrorCode.ALREADY_OPEN);
        case LOCKED -> throw new DoorException(DoorException.ErrorCode.IS_LOCKED);
        case CLOSED -> {
            cancelAutoLockTimer();
            state = State.OPENED;
            openCount++;
        }
    }
}

Why it matters

Interface components work the same way: a button can be default, disabled, loading or in error. Thinking in states and transitions helps me design every state of a component, including the easy-to-forget ones, and agree on them with developers.

UML

What it is

A standard visual notation for software. A state diagram shows the states as boxes and the allowed transitions as arrows.

In this project

I drew the state diagram before writing the code. It is redrawn below for this page. Every arrow is covered by at least one test.

Why it matters

A state diagram is a shared language: designers, developers and testers can all read it and check together that no case is missing.

TDD

What it is

Test-driven development: you first write a test that describes a behaviour, then the code that makes it pass.

In this project

The assignment required test-driven development. My report maps every transition of the diagram to a test, and every invalid action to the error code it must raise.

Why it matters

Describing the expected behaviour before the code is close to writing acceptance criteria before a design is built: everyone agrees early on what “done” means.

JUnit 5

What it is

The standard Java framework for writing and running tests. Each test has a name and checks, and a report shows which tests passed.

In this project

Separate tests cover the valid transitions, the counter and the auto-lock. Parameterised tests (@ParameterizedTest with @MethodSource) check every invalid action per state and verify the exact error code.

Why it matters

Because each impossible action has its own code, an interface can tell the user exactly what went wrong, “wrong PIN” rather than just “error”. That is the basis of a clear error message.

Why this matters for a UX/UI internship

Many interface problems come from states nobody designed: an empty list, a disabled button, a failed login. This project trained me to list every state and every impossible action first, and to plan a clear response for each. A state diagram is also something I can sketch with developers at the start of a feature.

What I learned and limits

I learned to model behaviour as states and transitions, that an error code is more useful than an error text because it does not depend on a language and is easy to test, and to write tests that say clearly what they expect.

Limits: the class has no user interface and was not tested with users. The assignment asks for an auto-lock after 5 seconds, but the code currently uses 0.5 seconds, the value chosen to keep the tests fast, and the PIN is still written into the code. Making both configurable is the next step.
